3. Pipeline de escaneo

sequenceDiagram
    participant UI as IntelligenceTab
    participant API as POST /api/intelligence
    participant REG as Tool Registry
    participant DIS as Dispatcher
    participant EX as Executor (tipado)
    participant DB as Supabase
    UI->>API: tools[] + target
    API->>REG: getExecutor(toolId)
    REG-->>API: Executor
    API->>DIS: executeTool(ctx, input)
    DIS->>DIS: lazy-init plugins si toolId=plugin.*
    DIS->>EX: execute(ctx, input)
    EX->>EX: egress-guard (assertPublicHostname)
    EX-->>DIS: ExecutionResult{output, findings}
    DIS-->>API: resultados crudos
    API->>API: buildResultMap + getPrimaryIp
    API->>API: buildScanResponse (lecturas tipadas)
    API->>DB: persist investigation + findings
    API-->>UI: response tipado {dns, ssl, email, headers, ...}

Flujo de hallazgos

  1. Ejecución: cada executor devuelve { success, output, findings, error? }.
  2. Mapeo: buildResultMap() arma un Map<toolId, output>.
  3. Lectura tipada: scan-response.ts lee con accessors tipados (ej. DnsLookupOutput → claves a/aaaa/mx/ns/txt/soa en minúscula).
  4. Score: risk-engine agrega severidad/confianza → score 0-100.
  5. Persistencia: investigation + findings + asset changes en Supabase.
Nota de keysLos executors devuelven claves en minúscula (a, aaaa). El scan-response tipado lee esas claves exactas — un bug histórico leía mayúsculas (.A) y dejaba la sección DNS vacía; quedó corregido y con test de contrato.

4. Tool Registry consolidado

El registro de herramientas se consolidó (C05) en un único módulo con registerTool() como entry point:

FunciónPropósito
registerTool({executor, definition})Registra plugins dinámicos con guard de colisión contra tools nativas
unregisterTool(id)Desregistra plugins al desinstalar
getExecutor(id)Resuelve nativo → plugin dinámico
listToolDefinitions()Devuelve 34 nativos + 9 orphans + dinámicos
isKnownTool(id)Guarda contra colisiones nativas
flowchart LR
    NATIVE["NATIVE_TOOLS (34)\ncon executor real"] --> LIST["listToolDefinitions()"]

Orphans (9): definidos en el registry pero sin executor propio — se ejecutan con fallbacks o se marcan como "no implementado". Son: dns.dnssec, dns.propagation, dns.zone, website.redirects, website.cookies, website.csp (implementados en la fase de consolidación) y 3 adicionales de catálogo.

    ORC->>DET: diff vs último snapshot
    DET-->>ORC: cambios detectados
    ORC->>DB: INSERT asset_change
    ORC->>AL: cambios de registrador / expiración / NS
    AL->>DB: INSERT siem_alert_logs
    AL->>EXT: Slack / Email / PagerDuty

Detección de cambios:

  • DNS: nameservers, registros MX que desaparecen, SOA serial, TTL.
  • WHOIS: cambio de registrador, fecha de expiración próxima (impulso de alerta), nameservers anteriores.

UI: HistoryPanel en IntelligenceTab (timeline con diff visual) y pestañas "WHOIS Alerts" / "DNS Alerts" en /security/audit con diff previousValue → currentValue y canal de entrega.

  • Timeout: 20s por modelo × 3 = 60s peor caso < maxDuration=120.
  • Reporte: el prompt pide un mermaid flowchart en el Plan de Acción; el UI extrae bloques con extractMermaidBlocks() y los renderiza con MermaidBlock (dynamic import).
  • Gráficos: tableRowsToChartData() convierte la tabla de rendimiento en datos para el bar chart recharts.
  • Fallback resiliente: sin API key o error, genera reporte precompilado con métricas reales.

14. Seguridad y RLS

  • Row Level Security: políticas en todas las tablas con withRLS(); defensa en profundidad contra fugas entre tenants.
  • Egress Guard: validación CIDR matemática IPv4/IPv6 (16 rangos privados + 7 IPv6), assertPublicHostname() y safeFetch() con timeout y redirect validado.
  • Rate limiting: decorator genérico con Upstash Redis, headers estándar, fail-closed en prod.
  • CSP: nonce por request + strict-dynamic + report endpoint.
  • Índices compuestos: migraciones 0014/0015 con índices en FK y consultas agregadas (GROUP BY en SQL, sin descargar tablas completas a JS).
